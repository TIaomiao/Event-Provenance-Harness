「让 LLM 在多个时间点里选对那一个」有没有人做过？

核查日期 2026-10-08 · 核查者 DSH · 只收公开文献，不含任何患者材料 · 每条的核验程度分别标注

结论（先说最要紧的）

这个问题不新。它已经被明确提出、系统标注，并在旗舰基准上评测过 —— 至少从 2022 年起。

决定性证据 EHRSQL（NeurIPS 2022 Datasets & Benchmarks）里有第三类时间过滤器 [time_filter_exact]，原文定义就是「指出一个确切时间，例如 last measurement」；它的 Option 参数「从过滤后的事件中选出一个确切事件（例如 first、last）」。该数据集 24,411 个问答对，93.2% 的查询至少用到一列时间，题目由 222 名医院工作人员在没有看过数据库 schema 的情况下提出。

也就是说：「从自然语言推断该取哪个时间点（first / last / 窗口）」是这条线的既有任务设定，不是我们发现的空白。

但结论不是「方向死了」，而是我们的任务设计把这道题做没了：EHRSQL 要求模型推断时间条件，而我们的 baseline 把时间条件声明给了模型——这就是 120/120 的来源。

一、决定性证据：EHRSQL 已经这么做了

EHRSQL: A Practical Text-to-SQL Benchmark for Electronic Health Records · Gyubok Lee, Hyeonji Hwang, Seongsu Bae, Yeonsu Kwon, Woncheol Shin, Seongjun Yang, Minjoon Seo, Jongyeup Kim, Edward Choi（KAIST 等）· NeurIPS 2022 Datasets and Benchmarks · arXiv:2301.07695 · 已正式发表 · 本篇由我直接读取原文页面核对

它的时间过滤器设计（原文要点）

过滤器作用谁决定
[time_filter_global]限定感兴趣的整体时间范围题目给出
[time_filter_within]限定两个以上医疗事件之间的时间段题目给出
[time_filter_exact]指到一个确切时间，例如「last 一次测量」Option：从过滤后的事件中选出一个确切事件（first / last）

时间还按三个因素系统分类：表达类型（absolute / relative / mixed）、单位（年 / 月 / 日 / 就诊 / ICU 访次）、区间类型（since / until / in）。

数据集里的真实题目（原文 Table 1 举例）

  • When was the first prescription time of patient 20000?
  • What was the last arterial bp [systolic] for patient 23042?
  • Tell me the last specimen test given to patient 51177 in 10/2105?
  • Tell me the medication that patient 3929 has been prescribed for the first time in 05/this year?

它的评测口径

两个指标：F1_ans（判断问题可答 / 不可答）与 F1_exe（执行准确率——只有数据库返回的答案正确才算对）。含**不可答问题**（需要外部知识或超出 schema），只在验证/测试集出现。

对我们的直接影响：不能声称「自然语言里的时间选择条件需要被推断」是新的问题；不能声称「first/last 选择」是新的任务类型。审稿人只要知道 EHRSQL，这两句话就会被直接打回。

二、这条线三代工作的分工

代代表「取哪个时间点」怎么定能不能当我们的创新
古典时间抽象 Shahar & Musen 1996（Artif Intell Med 8(3):267–298，DOI）；Stacey & McGregor 2007 综述（DOI）；Boaz & Shahar 2005（DOI） 窗口是输入的参数，由查询给出或知识库条目给定；KBTA 把原始值提升为区间概念（LOW/HIGH、INCREASING） 不能「把时序值抽象成区间」早已解决
时序 / 纵向建模 GRU-D（Sci Rep 2018，DOI）；BEHRT（Sci Rep 2020，DOI） 窗口是预处理超参，事先固定；时间用作衰减信号或位置嵌入 不能不规则采样与缺失处理也已解决
LLM 时代 EHRSQL（NeurIPS 2022，见上）；TIMER（npj Digit Med 2025，DOI）；MedAlign（AAAI-24，DOI）；TimeR4（EMNLP 2024，DOI）；EHR-RAG（arXiv:2601.21340，预印本） 由模型从题目推断（EHRSQL 的 first/last 槽位；TIMER 的时间戳接地与「时间边界遵守」；TimeR4 先把时间约束重写出来再检索） 部分机制已存在，但见第三节的四个残余缺口

上表古典与建模部分来自定向检索（核验到摘要与元数据级，Shahar 1996 全文付费墙；未逐篇通读全文）。这一限制如实标注。

三、还空着的四个位置（我们的机会所在）

  1. 输入是结构化 MIMIC-III / eICU，不是扫描病历。EHRSQL 直接在关系库上生成 SQL；没有人处理「记录在表格重建之前根本不存在」这一层。我们在 batch-full-01 实测：一行化验结果在 OCR 里是好几条独立行（项目名、别名、结果、单位、参考区间），只把项目名行交给抽取器 → 值+单位完整 0 条；按行带跨行重建 → 2,303 条明确记录。
  2. 「给选中的集合打分」也已经有人做了——但粒度和时间维度都还不够。 FHIR-AgentBench（ML4H 2025，arXiv:2509.19319）的官方评测脚本同时打两件事：① 金标准选中集合 true_fhir_ids（{FHIR 资源类型 → 资源 ID 列表}）上的 retrieval precision / recall / F1；② 用 LLM judge 判答案正确率。它的题目也确实要求在多个时间点之间消歧（例如「第一次住院当天第二次测量 vs 第一次测量」）。
    但两处不够 第一，选中集合的粒度只到 FHIR 资源 ID，没有「观测 ID + 显式时间点」这一级；第二，它没有时间角色标签（采集 vs 报告）。更有意思的是它的 judge 明确写了 「忽略单位（1850 = 1850 mL）」、日期「除非题目明确要求，可忽略时间与时区差异」 —— 也就是说单位错与时刻错在答案指标里根本不扣分。
  3. 没有把「采集时间 vs 报告时间」当作标注轴。我们能查到的基准里都没有这个维度；FHIR-AgentBench 的金标准只到资源 ID 级，TIMER 的金标准是 (问题, 回答, 时间证据) 但只用 LLM-judge / BERTScore / ROUGE-L 评回答文本，没有对时间证据做集合匹配。
  4. 「条件被声明 vs 必须推断」这个边界本身几乎没有被系统测量。我们自己的 240 条轨迹恰好测出了这条边界的一端（全部声明 → 两组满分），但这是我们的观察，不是既有工作。

四、这对我们的题目意味着什么

说法判定理由
「自然语言取数条件需要被推断」是新问题站不住EHRSQL 2022 已系统标注并评测
「first/last 时间点选择」是新任务类型站不住[time_filter_exact] 的 Option 就是它
「把时间约束先外化再检索」是新方法站不住TimeR4 等已是既有做法
「真实扫描病历上的记录层 + 选中记录集合评分 + 时间角色 + 未决状态」尚可辩护第三节四个缺口；但必须把「结构化库 vs 扫描件」的差异讲清楚，不能只说「输入不同」
「当前 baseline 无增量」是事实，且不丢人原因是我们把 EHRSQL 要求推断的条件声明了；师兄在会上也说了先跑通、创新点放后面

据此题目应改写成什么（草）

在真实扫描病历上，先把逐行 OCR 重建为可选择的「记录」，再检验当取数条件不再被声明、必须从自然语言推断时，模型能否选出正确的记录集合，并如实交出时间角色、来源锚点与未决状态——并以记录集合而非最终答案作为评分对象。

这个版本里，EHRSQL 是我们的对照与来源，不是我们要否认的既有工作。

五、我们的实测事实（与文献无关，自己测得）

  • 240 条轨迹：直接选择在原始输出下按修正参考 120/120；先计划再执行当时执行按修正语义 110/120，修正后离线重放才 120/120（重放不是新模型运行）。
  • 20 条差异全部来自我方参考的两处缺陷（窗口外计数、仅日期精度被当成 HH:MM:SS），不是模型错误。
  • 覆盖测量：10 个包里只有 2 个的采集序与报告序不一致，各 1 对倒序 → 时间角色维度覆盖充分但判别力很弱。
  • 记录层：batch-full-01 13,084 份文档，1,244 份检验报告全部进入抽取、0 schema/对齐失败；逐行 0 完整 vs 跨行 2,303 明确。

六、未核与风险

  • 未核：Shahar 1996 全文（付费墙，只核到摘要）；EHRSQL 的附录 B.2 时间模板全表（只核到正文 Table 3 举例）；MedAlign / TIMER 的技术全文（只到摘要与元数据级）。
  • 风险：EHRSQL 2.0 或后续版本未逐项核对；可能还存在我们没检索到的、已经做了「记录集合评分」的工作。
  • 低可信来源：clawRxiv:2604.00633 自称做了「按题目推断最窄可辩护时间范围」，但它是未经同行评审的预印本，只有 2 个病例、无基准比较，作者自称贡献是概念性的——不能当作既有工作引用，也不能当作已被验证的方法。

七、下一步三件事

  1. 把任务设计改成 EHRSQL 式：让模型从自然语言推断时间条件（first/last/窗口），而不是由宿主声明。这是唯一能产生非满分结果的改法。
  2. 把评分对象定在记录集合（含时间角色与来源锚点、未决状态），并在论文里明确写出这与 EHRSQL 的 F1_exe 的区别。
  3. 把记录层当作独立贡献：真实扫描件上「记录不存在直到表格被重建」这件事，是我们实测的、别人（结构化库路线）没有面对的问题。

相关问题要问师兄：这个改写后的定位他是否接受；以及是否同意把 EHRSQL 作为主要对照基准。
