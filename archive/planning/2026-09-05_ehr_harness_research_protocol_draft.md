| --- | --- | --- |

核验层级：文档与相关源码入口检查。未访问患者正文、运行产物私有状态或凭据；未运行原有测试、重跑 OCR、调用临床模型或修改服务器。

## 3. 参考工作的具体用途

### DataSpace：任务接口与 harness 对照

官方任务提供自然语言问题和异构工作区，要求提交结构化 CSV。公开部分参考答案和冻结评分配置；baseline 是使用 bash、view_image、submit_answer 的轻量 ReAct 系统。

论文包含固定同一模型比较多个 harness 的实验。harness 对照统一环境和 1,800 秒时限，保留各框架原生行动控制；不能写成所有预算维度完全相同。运行中提交工具检查格式，不向 Agent 提供参考答案正确性反馈。

可借鉴：共同任务契约、冻结参考答案、相同模型下比较控制流程、完整失败统计、token/费用/耗时记录。

区别必须准确：DataSpace 的构造来源已包括 EHRSQL 等临床数据，不能把差距写成“现有工作没有医疗数据”。当前候选侧重点是原生真实病历导出中的跨文档事实与时间关联；差距表述仍需针对相关工作逐项建立证据。

### HealthFlow：计划、执行、评估与受控经验

HealthFlow 接收临床分析需求和可分析的 EHR 数据，产出代码、统计结果、图表、报告及轨迹。它的四项职责为 Meta 制订计划，Executor 执行工具/代码，Evaluator 检查产物与约束，Reflector 提炼受控经验。

可借鉴：任务合同、错误反馈、有限重试、版本化轨迹。其报告评分不能直接替代本项目的字段、事件时间和证据正确性评价；支持 JSON 输入也不代表已解决 OCR 布局到纵向记录的映射。

复现注意：正式论文描述任务序列内的记忆更新，当前源码 README/runner 描述冻结 benchmark 写回。实际借用时需固定源码版本和记忆协议。本地旧笔记的任务数量与参考答案状态不能当作当前官方状态。

### 两张 keynote 海报

“Towards Agent-First Data Systems”提供面向 Agent 设计数据系统的定位；“The Post Developer Era”强调意图、需求和约束在系统构建中的作用。它们支持理解题目为何可上升到数据与 Agent 交互层，不能据此推断必须训练模型或堆叠多个 Agent。

## 4. 建议的研究工作定义

暂用如下工作定义组织实现，尚非最终标题或已验证贡献：

> 面向真实纵向 EHR 的 Data Agent Harness：按任务组织跨文档证据，调用通用模型提取与关联事实，生成带时间和来源的结构化病例记录，并检查输出中的冲突与不确定项。

此处 AI-ready 的第一版可操作含义是：数据满足选定任务的字段、事件粒度、时间与证据要求，可以被统一程序读取和评价。其对更广泛预测或表示学习任务的价值，需要相应实验再支持。

## 5. 优先搭建的三件交付物

### A. 任务与评测协议 v0.1

建议分三部分；这些分点不是对师兄原话的补全。

1. **任务/输出协议**：输入为同一匿名病例的允许使用证据和指定问题集合；输出为标量答案、事件表、来源引用及缺失/冲突状态。先从现有试卷选择少量典型任务，覆盖单文档字段、跨文档归并和重复事件。
2. **时间协议**：区分事件发生时间与文档记录时间；保留多次观测；明确相对时间锚点、不确定时间和冲突如何表达。若将来做时点预测或“截至某日”问题，再定义可见证据截止时间；完整病程回顾抽取不能与前瞻预测混用评价。
3. **模型与评测协议**：固定模型版本、共同证据来源和输出定义，冻结开发/测试划分、参考答案、重试上限与计分规则。评估用答案不给模型；测试集病例不得用于修改 prompt 或规则。

已用于规则调试的少数试填病例适合作为开发集。第一张诊断表可先在开发集产生；论文主表需要独立、具有足够任务覆盖的评价集。样本量在小试确认错误类型和标注成本后确定，不凭空指定最终规模。

**首轮评价范围**：优先提取原文明确列出的项目、数值、单位、明确日期/相对时间及来源位置。参考答案由人对照证据核验，预先规定匹配规则；程序按规则评分。模型生成的候选可辅助准备，但不能直接当作自己的标准答案。遇到原文或 OCR 含糊的项单独记录，逐步报告其比例与影响。

医生参与先集中在必须使用临床知识的定义与歧义，例如推断分期、判断复发、划分治疗线次或取舍冲突诊断。第一轮任务可以先选原文明示事实；医生反馈不作为所有原型工作的前置条件。评价要求取决于论文主张，计算机会议同样需要可信参考，但未必需要大规模临床专家标注。

### B. 可切换模块的最小 harness

建议执行路径：

```text
问题/目标字段 + 病例证据索引
    → 选择相关文档与最小证据片段
    → 调用已有几何解析或模型抽取
    → 关联病例主体、事件及时间
    → 检查 schema、来源支持、重复与冲突
    → 有限范围补查/修复，或保留 unknown/待复核
    → 输出统一答案与执行轨迹
```

模型负责语义抽取、证据选择与需要语言理解的关联；确定性程序负责索引、格式/枚举检查、时间运算和评分。检查引用存在只是基础校验，来源是否真正支持答案需要单独评价。

可将执行组织为证据抽取、时间关联、结果核验三个职责。先让各职责在同一运行器中工作；是否实现为多个 Agent，以及是否带来质量/成本收益，由对照决定。初版先固定经验，不引入跨测试病例持续学习。

### C. 第一张对照结果表

下表是逐步扩展的实验顺序。起步只比较“同一模型直接抽取”和“增加一个明确模块”，拿到结果后再扩展条件。

| 条件 | 做什么 | 用途 |
| --- | --- | --- |
| 现有规则/Python | 现有解析器生成待评分的候选答案 | 记录工程基线实际能力 |
| 同一模型直接抽取 | 共同输入处理后，用固定 schema 提示词直接生成答案 | 建立有竞争力的直接模型基线 |
| 同一模型 + 分阶段 harness | 证据选择、抽取、病例归并与时间关联 | 观察组织过程的增益与代价 |
| 同一模型 + 完整检查循环 | 增加来源/时间检查与受限修复 | 检验验证环节的增益与代价 |

完整版本再分别去掉时间关联、来源核验等模块做消融，避免只比较完全不同规模的系统。若多个 Agent 比单模型多消耗调用，应增加预算匹配或质量—成本曲线。

首轮至少报告字段正确性、事件及时间关联、来源支持/定位、无依据回答与适当拒答、覆盖率，以及 token/调用次数/耗时。格式错误、超时、未完成和无法回答分别记录，主表不只留下成功样本。按同一病例内多个字段的相关性汇总，正式统计避免将所有字段视作完全独立样本。

数据规模可以用于后续分层扩展和吞吐/成本曲线；评价质量仍需要可靠标注子集。大量未标注输出可用于覆盖率与运行成本统计，不能自动成为准确率证据。

## 6. 实施顺序与判断边界

1. 先完成一页 motivation—gap—设计主张草稿，与第一版任务协议相互检查；gap 使用已读相关工作证据。
2. 复用现有问题库、source_refs 和模型契约，做合成证据上的运行器/评分贯通。
3. 按已获批范围接真实样本，形成直接模型与分阶段方案的第一张开发集诊断表；外部模型需沿用当前项目的供应商和数据范围授权要求。
4. 根据错误分布集中改时间关联或证据检查，再扩展独立测试集与规模评价。

可能推翻设计预期的结果包括：直接模型在相同预算下已经同样准确；多 Agent 仅通过更多调用获益；错误主要来自 OCR 或临床定义歧义。遇到这些结果时，调整模块和主张，把实测差别写清楚。当前推荐实施路线的置信度为中；效果与创新性未由本轮实验建立。

当前数据记录明确缺少可支持完整随访结局的来源，因此第一轮以已有文档内的事实与事件重建为主，不预设 OS/PFS 等结局预测任务。

排期信息：目标会议偏计算机方向；MICAD 为用户转述的备选，具体会议、投稿类型和截止时间仍待核验。近期先按小型实验周期推进。

## 8. 大二首次科研：第一轮怎么投入

以下是可调整的起步安排，以每周 10 小时主动研究时间为例，不代表用户已经承诺该时长。机器运行与等待不计入个人投入。

| 主动投入 | 做什么 | 本周留下什么 |
| --- | --- | --- |
| 2 小时 | 读 DataSpace 的任务定义、baseline 和关键结果表；带着本项目的问题看 HealthFlow 的方法图 | 每篇几句话：输入输出、比较条件、哪项结果支持哪项设计 |
| 3 小时 | 对照少量允许使用的证据整理答案，逐条看模型输出错误 | 小型参考集、错误表；先判断值、时间、证据分别错在哪里 |
| 3 小时 | 决定一个对照变量，交给 Codex 实现和运行，再检查产物 | 一份实验配置、一张真实结果表 |
| 2 小时 | 写清本轮发现，准备向师兄汇报 | 200–300 字：比较了什么、发现什么、下一步为什么这样改 |

### 三件交付物对应的个人动作

1. **协议**：拿两三个例子，把“输入给什么、输出长什么样、怎样算对”讲清楚。先写一页研究卡，Codex 再转换成 schema 和评分脚本。
2. **原型**：画出几步处理流程，选择本轮要增加的一个环节，检查 Codex 的实现是否符合设想。研究精力集中在设计与结果，工具接线由 Codex 承担。
3. **结果表**：亲自检查失败样例，解释两个条件为何不同，决定下一轮只改变哪一个因素。Codex 负责汇总、制图和保存配置。

### 第一周的五次工作单元

每次约 1.5–2 小时，可按课程安排移动；时间是起步预算。

1. 写五行研究卡：本轮任务、允许输入、预期输出、一个设计假设、比较方式。阅读仅围绕填完这张卡。
2. 选 10–20 个原文明示的题目实例，对照来源写参考答案和匹配规则。这个规模用于调试流程，不代表最终论文评测规模。
3. 让 Codex 复用现有模型契约接通直接抽取与评分。实际运行沿用获批模型和数据范围；合成样例可先验证执行链。
4. 亲自检查结果，按字段错配、时间错配、漏提取、无依据补全等归类，选一个占比较高且可解决的问题。
5. 让 Codex 加一个针对性模块，在同一批开发实例上对照；写一小段结果解释。得到差异后再决定第二周的规模与模块。

第一周完成标准：能用自己的话解释任务、比较条件和主要错误；留下一页研究卡、小型参考集及其来源、一次可重跑结果。尚未有可靠差异时如实记录，后续据此调整实验。

### 汇报时可直接使用的表达

> 我准备研究怎样组织模型处理真实病历证据，生成带时间和来源的结构化记录。本轮先比较直接抽取和增加一个处理环节后的结果。我正在明确输入输出、评价方式和错误类型，后续根据结果选择需要深入的模块。

把“我看到的事实”“我猜测的原因”“下次怎么检验”各写一句，即可形成一次有效的科研汇报。术语与标题可随理解逐步调整。
