# benchmark 数据集构造协议（2026-09-17）

师兄给的指令：**"得构造数据集。你现在有数据，但需要先通过你的 agent 或者 deepseek + 人工审核和反馈的一部分，
来做个 benchmark 数据集。数据集的答案不一定特别准，之前的大模型的 benchmark 就是这样做的。"**
另外加一个维度：**一次性完成率**。

本文档把这条指令变成可执行的东西。

---

## 一、要造的是什么

| 项 | 定 |
| --- | --- |
| **评测单位** | **一个病例**（因为"一次性完成率"是按病例算的） |
| **任务** | 按已有契约抽取：**16 张事件表 + 49 个标量问题**（`case_level_question_bank.v0_2.json`） |
| **首期范围** | 先把 `laboratory_observations` 一张表做透（现在就是），再逐张扩 |
| **首期规模** | **30 个病例**（现在 12 个），其中 **6 个作校准集、24 个作评测集**，两组不重叠 |
| **答案键版本化** | 沿用现有做法：冻结 + `sha256` + manifest（参照 `gold_standard v0.30`） |

## 二、答案键分三层做（这是关键）

**不能只用模型造答案键，否则就是自己考自己。**分三层，每条答案都标上它来自哪一层：

| 层 | 谁产出 | 负责什么 | 现状 |
| --- | --- | --- | --- |
| **L1 机械层** | 格子几何，**不来自任何模型** | 每行有哪些项目、值是多少、值印在第几行、页脚时间 | ✅ 已有，**待校准** |
| **L2 模型层** | **一个比被测模型更强的模型**（记录名字和版本） | 项目名归一化、单位归一化、叙述文档里的字段、`answer_status` | ⬜ 要做 |
| **L3 人工层** | 我们自己抽查（**不需要医生**） | 核对 L1/L2 的抽样，报告一致性 | ⬜ 要做 |

### 必须避开的坑：循环论证

**如果答案键是用"被测的那个模型"生成的，评测就是自己跟自己比，必然接近满分。**
之前 MMLU 那一类 benchmark 的做法是：**题目和答案由人写**，模型只生成"候选答案"。

所以三条硬规则：

1. **造键的模型 ≠ 被测模型。** 键里记录造键用的模型名和版本。
2. **留一个从没参与造键的模型做留出评测**，否则审稿人一定会问。
3. **每条答案标注来源层（L1/L2/L3）**，这样审稿人能看出哪部分是被验证过的、哪部分是模型生成的。

## 三、答案键不完美怎么办（师兄说"不一定特别准"，这句要接住）

承认不完美可以，但**必须把"键本身有多准"报出来**，否则整篇论文的准确率都是浮沙。

| 做法 | 具体 |
| --- | --- |
| **抽样人工核** | 在 6 个校准病例上，我们**逐行**核对 L1 机械层（不用医生，自己核） |
| **报一致性** | 报"人工核过的行里有多少跟自动键一致"，给出比例和区间 |
| **按患者聚类算置信区间** | 同一患者的记录不独立，**按病例做 cluster bootstrap**，不能按行 bootstrap（否则区间假窄，审稿人会抓） |
| **写清键的来源** | 每张表的键写：哪一层产出、谁核过、核了多少、一致率多少 |
| **错键的处理** | 发现键错了就改键并升版本号，**不要为了凑结果改评分器** |

## 四、一次性完成率（师兄新加的维度）

**定义**：一个病例算"一次性完成"，当且仅当在**一次调用、无人干预、无需重跑**的前提下：

1. 返回的是可解析的 JSON（没被截断、没坏）
2. 这个病例确实返回了行（不是空）
3. **行数达到几何真值的 90% 以上**
4. **所有引用都解析得到真实存在的行**（100%）

任一条不满足 → 需要重跑或人工介入 → 不算完成。

**辅助报三个数**：平均重跑次数、人工介入次数、每个病例的成本。

### 现在就能算的结果（12 病例，单次调用）

| 系统 | 返回了行 | **一次性完成** | 完成率 | 每病例成本 |
| --- | --- | --- | --- | --- |
| 整病例一次问 | 9/12 | 6/12 | **50%** | $0.07 |
| 同类文档合并一次问 | 8/12 | 6/12 | **50%** | $0.04 |
| 逐文档分开问 | 9/12 | 7/12 | **58%** | $0.05 |

没完成的病例分两类，**必须分开看**：

- **一个字都没吐出来**（CASE-02/06/100）：输出预算不够，JSON 被截断 → 工程问题
- **吐出来了但行数不够**（CASE-03 三种问法都是 127~128/200）：抽取不足，**也可能是我真值算错了**

**这个数字是现在唯一"能分开系统、又不需要医生"的指标，而且还有很大提升空间（一半病例跑不通）。**

## 五、论文的 claim 因此可以定下来

现在的故事线是：

> 现成的单次调用**只能一次跑通一半病例**；一个 agent harness（拆分 + 自验证 + 有预算的重试）
> 把一次性完成率从 ~50% 提到 X%，成本只增加 Y%。

这条线的好处：**有效性有明确度量（完成率）、有提升空间、有成本轴、不需要医生**。
而且和我们已知的失败原因对得上（大病例输出预算爆掉、行数抽取不稳）。

**待定**：X 和 Y 是多少，取决于 harness 怎么做。这是下一步要跑的实验。

## 六、执行顺序

| 步 | 事 | 成本 | 依赖 |
| --- | --- | --- | --- |
| 1 | 校准 L1 机械层（6 个校准病例逐行人工核） | 0 | 无 |
| 2 | 定 30 病例的分层抽样（按病例大小、文档数分层） | 0 | 无 |
| 3 | L2 模型层跑一遍（强模型造候选）+ 与 L1 交叉 | ~$5 | 步 1 |
| 4 | L3 抽查 + 报一致性与区间 | 0 | 步 3 |
| 5 | 冻结 v1.0（sha256 + manifest） | 0 | 步 4 |
| 6 | 在 v1.0 上跑基线（≥6 类，含"单次 LLM 无 agent"） | ~$10 | 步 5 |
| 7 | 跑 agent harness 消融，出完成率—成本帕累托 | ~$15 | 步 6 |

**步 1 和 2 不用花钱，今天就能做。**

## 七、边界（不遮掩）

- 首期只有 **30 个病例**，池子里有 200 个。
- **只有一个人核**（我），没有第二标注者 → 报不出真正的 inter-annotator agreement，只能报"我核过的行里自动键的一致率"。**这一点要提前跟师兄说清，别等到审稿人被问。**
- 没有医生金标准，所以 **"临床等价匹配（CEM）"这一层做不了**，只能做字符串与数值层面的严格匹配。师兄设计文档里提到"心梗 vs 急性心肌梗死"那类问题，我们答不了，要如实说。
- L2 用强模型造键，**必须和被测模型分开**，并且留出一个没参与造键的模型。
