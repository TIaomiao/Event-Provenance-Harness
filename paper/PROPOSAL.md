# EHR Harness 论文 Proposal

版本：v0.1（2026-09-08）。本文件是当前 Proposal 正文入口；本对话负责总控和版本整合。详细的调研反驳和来源表见 [KDD Idea Review](KDD_IDEA_REVIEWED_2026-09-08.md)。

## 题目

**Event-Provenance Harness: Query-Conditioned Structuring for Verifiable Analytics over Real-World Longitudinal EHRs**

## 中心命题

真实纵向 EHR 的难点不是把 PDF 转成 JSON，而是把分散、重复、冲突且时间含义不同的证据组织成带事件身份和来源的可验证记录。我们研究一个按查询物化事件、显式表达时间与来源、并由执行评测器检查结果的 Data Agent Harness。

## Motivation

1. 同一指标可能被多份报告重复引用，也可能在不同时间真正复测；简单键值抽取、RAG 或直接生成表格容易发生值—时间—来源错配、错误合并和无依据补全。
2. DataSpace、ClinLens、HealthFlow 等工作已经把异构证据、纵向任务和执行评测推到前台，但真实 PDF EHR 的事件身份、时间角色和来源关系仍需要独立的任务接口与受控评价。

## 三项创新候选

1. **Temporal-Provenance Event Identity Layer**：把事件身份、事件时间/文档时间、来源 bbox、重复、冲突和不确定性作为可判定对象，区分重复描述与真实复测。
2. **Query-Conditioned, Uncertainty-Aware Event Materialization**：根据分析任务和不确定性选择要物化的事件与证据，必要时补查，无法确定时保留 `unknown/conflict`，并记录可回放轨迹。
3. **Execution-Grounded EHR Harness and Evaluator**：在真实肺癌 PDF 和可控扰动任务上，固定模型、证据和预算，分开评估值/单位、时间、来源、重复保留、错误合并/拆分和质量—成本曲线。

## 我们的数据优势与边界

现有 inventory 记录约 39,560 个病例目录和 462,789 份 PDF；这首先是目录/文件规模，不能直接写成独立患者数或科研可用样本数。与常见 KDD/医疗 Agent 工作相比，真正有区分度的优势是：

- 原始医院 PDF 的文档级异构性、跨页版式和 OCR/bbox 证据，而不是已经整理好的 MIMIC 表或 FHIR 虚拟 EHR；
- 同一病例多文档、多时间点、重复报告与真实复测共存，可观察事件身份和时间角色错误；
- 能以真实数据分布做压力测试，再用合成扰动构造可控评价；
- 规模足以报告不同文档长度、重复程度、时间歧义和 OCR 质量下的质量—成本曲线。

常见对照数据源包括：公开去标识结构化 EHR（MIMIC、EHRSHOT、UK Biobank）、FHIR/模拟 EHR（MedAgentBench）、合成或渲染 benchmark（DataSpace、FDABench），以及少量真实医院/多中心数据。HealthFlow 已用公开 MIMIC-IV Demo 和 485 例 COVID 时序数据建立 100 项 EHR 分析任务；ClinLens、ClinTraceBench 和 EHR-Complex 也已覆盖纵向任务、来源或执行评测。因此“真实、规模大、用了多 Agent”都不能单独作为创新。

KDD 卖点应写成“真实 PDF EHR 文档分布 + 事件级任务协议 + 可控执行评测”，并公开不含患者内容的 schema、评测器、合成伴随集和匿名聚合统计。需要向师兄/数据负责人确认的真实数据统计包括独立患者数、文档数、事件数、时间跨度、重复率和可用于评价的病例数。

## 首轮实验

重复检验的值—时间—来源匹配是 E1 切入口，不是整篇论文的最终范围。对照为同一模型直接抽取 vs. 事件身份/时间/来源组织后抽取。首轮先做原文明示事实，使用合成边界和少量获准开发样本；真实模型效果尚未产生。

## 现有基础与缺口

- 已有 OCR/bbox、脱敏、病例级事件表、来源引用和统一模型接口。
- 时间候选适配器 v0.3.1 已完成局部工程验证，日期角色与检验行绑定仍待完成。
- 事件身份归并、查询驱动物化、评分器、独立参考集、真实 A/B 和消融实验尚未完成。

## 必须证明的三件事

1. 事件身份机制确实区别于普通 ETL/RAG/去重，而不是换名或增加字段。
2. 在相同模型、证据和可比预算下，机制能减少关系错误，并且收益不只是更多调用带来的。
3. 独立评测能够判断来源是否支持正确事件，而不是只检查引用格式。

如果这些证据没有出现，主张应降为单中心纵向 EHR 开发切片上的受控事件匹配实验，不能宣称通用 AI-ready substrate 或 KDD 级 benchmark。

## 师兄对齐问题

1. 主贡献更偏事件级数据表示、查询驱动 Harness，还是执行评测协议？
2. “多时序、模型层、protocol”具体指什么机制，最接近哪篇论文或方法图？
3. E1 作为第一轮是否合适，下一阶段应该扩展哪些事件或分析任务？

## 你接下来补的能力

- 每读一篇论文只回答四件事：输入是什么、输出是什么、核心机制是什么、怎样证明有效。
- 把论文机制改写成一个纯合成例子，先观察边界，再让 Codex/DSH 接口化；不要先追求完整复现。
- 读一段 evaluator 或 baseline 代码，说明它怎样定义“答对”和“预算公平”；这比继续堆论文标题更有帮助。
- 每周做一次三分钟口头复述：一句主张、一个反例、一项实验、一个待师兄决定的问题。
- 把模型/Agent 研究和数据层问题分开记录：模型能抽取什么，事件结构如何保存，评测怎样判断来源支持，分别对应不同学习任务。
