## 题目

**AI-Ready by Measurement: How Much Database Preparation Does an Off-the-Shelf Agent Actually Need?**
（中文：**给现成 AI 用的医疗数据库：到底要准备到什么程度**）

备选副标题：`A five-version superset ladder over 984 real hospital cases, measured with five metrics.`

## 中心命题

**"AI-Ready"被当成一个标签用，没有被当成一个可测量的量。**

真实医院 PDF 做成数据库时，每一步加工（统一格式、归一单位、加溯源、加说明书）都被默认为"对 AI 有帮助"。但**没有工作把这句话放在同一批问题、同一个没参与建库的模型上逐层测量过**。我们把它测出来，并且发现收益的形状和直觉不同：

- 在**单病例**问题上，加结构化层**没有准确率增益**，收益几乎全在成本（同一批题，单位成本的做对题数相差约 5 倍）；
- 把结构化层当成**原文的替代**会明确变差（有损摘要），所以 **AI-Ready 层必须是附加的、不是替代的**；
- 在**跨病例聚合**上，"AI-Ready"的性质从"省钱"变成"**能不能做**"：原文 12 个病例就超过模型上下文上限（1,048,576 token），而结构化层一次装下整批 **984 例**。

## Motivation

1. **真实数据的形态决定了瓶颈在哪。** 我们的语料是 39,560 个病例目录、462,789 份 PDF 的原始医院导出，OCR 覆盖 90.8%（33,456 例 / 410,467 文档 / 2,130,171 页已处理）。这些 PDF 是**扫描件 + 印刷表格 + 印章 + 多版式**，不是 FHIR 资源、不是 MIMIC 表。现有"AI-Ready"评测的输入多是**合成或已成结构化的数据**（例如 FHIR bundle），而真实版式上的可读性、单位印刷形、参考区间、跨文档对齐都没有被覆盖。

2. **临床侧已经承认这是一个等级问题，但只有人工量表。** 例如 J Clin Med 2026 用 0–2 的人工"AI-Ready"分级评价病历质量。人工量表的问题是：**换一个模型、换一批问题就可能翻转**，而且无法回答"再加工一步值不值得"。我们要的是**由下游 AI 表现定义的、可复现的度量**，而不是由人工标签定义的等级。

## 贡献（按证据分级）

1. **主贡献｜一个可复现的 AI-Ready 度量与它的曲线。** 五个严格超集的数据库版本（生数据 → 格式统一 → 单位归一 → 溯源与状态 → 机器说明书），同一批问题、同一个**没参与建库**的消费者模型、一次调用、不给例子；产出**正向曲线**（逐层加东西值多少）与**反向拆件**（从完整版逐层拿掉一样东西掉多少）。五个指标覆盖做对率、费劲程度、错答结构（含错否定）、该说不知道时、以及**可核对性**（引用可解析率 + 走到原文的步数，作为医生核对时间的代理）。
   *诚实说明*：这里的"分层加料"思路在文献里已有近似形态——FHIRBench（medRxiv 2026-07）比较过几种序列化格式并报告"更紧凑的格式更好"，另一篇 FHIR 序列化工作（medRxiv 2026-08）比较格式相关的可读性。**我们与它们的差别是对象与维度**：对象是真实扫描 PDF 与真实版式，维度是五个版本 × 五个指标 × 病例级与队列级两个尺度，而不是单一格式对比。这一条属于**增量**。

2. **机制｜附加式 AI-Ready 层与它的容量边界。** 我们用同一批问题给出一个可复现的容量对比：原文在 10 个病例以内可答、12 个病例即超出上下文；结构化层在 984 个病例（整批）上仍可答且基本正确；并给出 33,456 例规模上原文约 6.4 GB ≈ 21 亿 token 的推算。结论写成设计约束：**AI-Ready 层必须是叠加在原文之上的，不能替换原文**。
   *诚实说明*：`HoloBench`（arXiv 2410.11996）已经建立了"上下文变长时聚合任务退化、而最大/最小这类操作抗退化"的观察，我们的队列级结果**复现了同一现象**（984 例时计数出现 ±1~2 的偏差）。这一条属于**部分被占**，我们的增量在"容量"这一维度（能不能装下）而非"退化曲线"。

3. **对象｜真实扫描 PDF 上的机械答案键与临床契约层。** 答案键由**几何层**产出（读印刷表头 → 按列心绑格 → 按行距聚类成行 → 解析数值/单位/参考区间），**零模型参与**，因此不存在"出键模型 = 被测模型"的循环论证；键的误差用一条不依赖行聚类的独立口径校准（130 份检验文档一致率 85.3%，逐项 recall 88~99%）。在此之上，库对外暴露的是病例级契约：49 个标量问题 + 16 张事件表 + 9 种答案状态码 + `clinical_model_io.schema.json`。
   *诚实说明*：面向 EHR 的 agent benchmark（EHRSQL、MIMICSQL、MedAgentBench）都**假定数据库已经存在**，因此"契约层"本身不是新的科学发现。这一条的价值在于**它是真实 PDF 上的契约层**，且被同一批实验当作可测对象使用；相对前两条，这一条的新颖性最薄。

## 与既有工作的边界（动笔前必须引用）

| 相邻工作 | 占据了什么 | 与本工作的关系 |
| --- | --- | --- |
| FHIRBench（medRxiv 2026-07-14.26358020） | 合成 FHIR bundle 上比较序列化格式，4 模型 × 3 任务 × 100 bundle，结论"紧凑格式更好" | **最接近的先例**；我们的差别是真实扫描 PDF、五层超集阶梯与五指标 |
| Context-Dependent FHIR Serialisation（medRxiv 2026-08-05.26359794） | 序列化格式对可读性的影响 | 与我们共享"格式决定可用性"的论点，对象是 FHIR 而非扫描件 |
| HoloBench（arXiv 2410.11996） | 长上下文聚合随规模退化、max/min 抗退化 | 我们的队列级结果与其一致，必须引用而非声称新发现 |
| SLIDERS（arXiv 2604.22294） | 长上下文（6~11M token）上的结构化抽取与编码对账 | 证明"长上下文抽取"已有系统级工作，我们只做度量层 |
| EHRSQL / MIMICSQL / MedAgentBench | 假定已有数据库/表格，评测 SQL 与临床任务 | 说明"契约层"不是我们的新贡献；也说明我们的对象不同（先有库才轮到它们） |
| J Clin Med 2026《From Medical Records to AI-Ready Data》 | 人工 0–2 级 AI-Ready 量表 | 我们主张的正是**量表 → 可复现度量**的替换 |
| ACIE / CCLM 2025 等抽取与可比性工作 | 抽取质量、跨实验室可比性 | 提供"抽取准确率已不是主要错误源"的背景，支持我们把度量重心放在可用性与成本上 |

## 数据优势与边界

优势是**对象**，不是规模数字本身：真实医院扫描 PDF、印刷表格几何、印章注释层、跨文档多时间点、文档类别多达 19 种（每 400 例统计：医嘱执行 788 / 检验 488 / 影像 458 / 病案首页 400 / 入院记录 399 …）。

边界：
- **无医生金标准**：内容正确率与临床等价匹配做不了，指标全部落在"机械可判 + 可核对"这一层。
- **单人核对答案键**：报不出标注者间一致性（κ）。
- 几何层答案键有 88~99% 逐项 recall，绝对做对率带不确定度；**跨版本比较不受影响**（所有条件共用同一键）。
- 目前 1 个消费者模型（网关型号逐轮记录）。
- 印章（BJCA 注释层）经实测**不遮挡文字**（去除前后 6 页暗像素变化 −9~+5），治理流水线已实现其去除；它不是 AI-Ready 的缺口。

## 必须证明的三件事

1. **度量不是换名的准确率**：换一个模型、换一批问题，五版本曲线的**形状**（哪一层值钱、哪一层不值钱）是否稳定。
2. **收益不是"更多 token"带来的**：同一条件下，超集与拆件条件的差异必须来自那一层本身，而不是上下文长度。
3. **可核对性是真实的**：引用可解析率与定位步数要能被人工抽查复现（挑病例做原 PDF 红框对照）。

若这三件事不成立，主张应降为"单中心真实 PDF 切片上的一次分层可用性测量"，不能宣称通用的 AI-Ready 评测协议。

## 师兄对齐问题

1. 队列级题（"整批里有多少例…"）是否就是你说的"跨病例"？题的规模与题型要不要再往临床分析上靠（例如"有多少例的某项指标在治疗前后跨过阈值"）？
2. "医生核对时间"要不要做成**真人小样本实测**（例如 30 条答案，两位医生计时）？现在我们只有代理指标。
3. 五个版本里有没有你觉得**该有但不在**的一层（例如随访时间轴、诊断编码对齐）？
