# PAI、HealthFlow 与我的 EHR 数据治理研究路线

整理日期：2026-08-25  
材料来源：与 DPSK 的讨论、师兄分享线索、用户提供的 PAI / HealthFlow 文章、本地 HealthFlow 源码拆解与实习项目文件。  
核验状态：HealthFlow 有本地源码快照可做结构分析；朱英豪公开 CV / 个人主页与北大医维矩阵实验室个人页确认了 PAI 的题目、KDD 2025 条目及公开合作关系。PAI 的实验协议、代码与数值结论仍未完成论文原文级核验。本文不是论文复现报告，也不是对外宣传稿。

## 先给结论

PAI 和 HealthFlow 不是两个孤立的“热点论文”，而是两个不同层级的研究模板：

- **PAI** 处理一个具体方法问题：EHR 缺失值是否一定要先恢复成一个看似真实的数值，以及如何让缺失表示直接服务于下游任务。
- **HealthFlow** 处理一条完整分析链路的问题：智能体怎样在队列、特征、建模、报告和复盘过程中守住时间泄漏、患者级切分、缺失处理和证据审计。
- **我的 EHR 治理工作** 位于两者之间的“数据证据层”：先保证 OCR、bbox、脱敏、人工复核、病例级问题和缺失状态可追溯，再把这些状态接到模型或 Agent 评估上。

因此，我不应直接复制某一篇论文，也不应把“读过论文”写成做出论文结果。更合适的路线是：

```text
真实 EHR 证据与治理边界
  → 缺失状态和病例级问题定义
  → 治理评估器 / 护栏 benchmark
  → 一个明确的下游任务
  → baseline、对照、失败案例
  → 小规模模型或 Agent 实验
  → 可复现表格和论文材料
```

## 一、信息分级

- 当前真实 EHR 试点保持本地处理，外部 API 调用为 0；没有把数据标记为 API-ready，也没有完成病例级 L3 科研结构化。

## 二、PAI 到底给我什么启发

### 方法学核心

PAI 的关键不是“把缺失值问题消灭”，而是质疑“先把缺失值填成一个拟真数值，再让预测模型使用它”这一默认流程。根据用户提供的论文介绍，它用按特征 / 缺失位置学习的 prompt 向量代替传统插补值，直接由下游预测损失优化，并为 prompt 与 backbone 设置不同学习率。

这可以改写成一个更准确的问题：

> 缺失信息的最佳表示，应该由插补误差决定，还是由具体预测任务和评估指标决定？

### 对当前 EHR 流水线的直接对应

当前标准试卷已经区分：

- `not_applicable`：临床上不适用；
- `source_document_absent`：导出中没有该类文档；
- `ocr_failed`：页面看不清或 OCR 失败；
- `parser_failed`：有证据但解析器失败；
- `redacted_unrecoverable`：原图被遮挡；
- `unknown`：目前无法判断。

这些不是同一个“空值”。它们代表不同的数据生成、流程或权限机制。若今后做 PAI 风格实验，第一步不是把它们全部替换成 0 或均值，而是先回答：

1. 哪些状态属于真正的临床缺失，哪些属于治理流程缺失？
2. 文档是否出现、某项检查是否被开立、某字段是否被结构化，是否本身就是预测信息？
3. 这些状态在不同中心、科室、医生和文档模板之间是否稳定？
4. 预测任务的 index time、标签窗口和特征可用时间是否已经固定？

### 未来可做的最小实验（还没有做）

在获批的匿名 L3 试填数据和明确标签之后，可以比较：

| 条件 | 表示方式 |
|---|---|
| A | 训练集拟合的均值 / LOCF 等静态插补 |
| B | 插补值 + 缺失 mask |
| C | 规则化缺失状态编码，不做数值伪造 |
| D | 可学习 token / prompt，按下游任务优化 |
| E | 简单规则、小模型和 PAI 风格方法的统一对照 |

最低要求是病例级切分、固定时间锚点、独立测试集、多个随机种子、主指标和失败案例。若只有一项任务、一次运行和一个漂亮均值，不能称为 PAI 复现或论文结果。

## 三、HealthFlow 给我什么启发

### 本地源码能够确认的设计

- Meta 先读取任务、数据画像、风险标签和受控经验，生成结构化计划。
- Executor 在受控工作区执行代码和工具调用。
- Evaluator 不只看最终回答，还检查完成度、范围保真、可恢复性、诊断质量和反思价值。
- Reflector 按任务结局控制经验写回：直接成功可写工作流 / 数据集锚点 / 代码片段；修复后成功最多写一条护栏和有限过程经验；失败轨迹只允许写护栏。
- EHR 风险预检把时间泄漏、目标泄漏、患者级切分、时间契约和队列定义显式化。
- 数据集锚点要求同数据集匹配，护栏按风险标签匹配；这比把全部历史对话塞进上下文更可控。

### 与我的治理工作的重合点

当前治理链路已经有一套“不可越过的门槛”：

- L2 脱敏未通过，不能进入 L3 或外部 API；
- 文档自动状态与人工审核状态分开保存；
- 失败、低置信度和疑似敏感文本进入 Quarantine，而不是猜测后放行；
- schema 版本、批次状态、反馈和证据位置可追踪；
- 标准试卷要求每个答案有 `source_refs` 或明确缺失状态。

这说明我可以先做一个 HealthFlow 风格的**治理评估器**，不必马上搭完整四智能体系统：

1. 对文档分类、脱敏、缺失状态、表格行绑定、时间顺序和诊断角色建立小型任务集；
2. 用规则 baseline 或现有 parser 生成结果；
3. 用 Evaluator 检查证据引用、范围保真、失败关闭和病例级一致性；
4. 把真实失败归纳为护栏候选，经过人工确认后再加入规则测试；
5. 输出错误类型、可恢复性、人工复核成本和版本化报告。

这比立刻复制完整多智能体框架更适合当前权限和能力边界，也更容易留下我能解释的代码和实验表。

## 四、对两篇工作的对抗式审查

### PAI

**结论**：PAI 是值得学习的“任务导向缺失表示”方法模板，但“无需插补”不等于缺失机制、偏差和外部泛化问题已经解决。

**反驳 / 反例**：

1. 可学习 prompt 仍然是在模型内部为缺失位置提供参数化表示，本质是替代传统插补，不是恢复真实观测值。
2. 如果缺失模式携带医院、科室或流程信息，模型可能学到机构偏差；随机缺失实验不能代替跨中心验证。
3. 只对比静态插补，可能高估方法优势；至少应补充 mask、缺失指示、时间衰减和更强联合模型基线。

**边界**：它必须依赖明确下游标签、严格切分和仅在训练集更新的参数；对于 `source_document_absent`、`ocr_failed` 等治理状态，不能直接套用数值时序插补假设。

**替代解释**：提升可能来自更合适的缺失 mask、优化器 / 学习率配置、数据预处理差异或特定数据集的缺失机制，而不一定全来自 prompt 设计。

**状态**：论文方法理解 = 用户材料 + 待核验；本地复现 = 还没做；当前 EHR 应用 = 推测；任何效果结论 = 未建立。

### HealthFlow

**结论**：HealthFlow 更像“科研工作流可靠性与审计”的系统研究模板，和我的治理基础设施有直接交集，但 benchmark 得分不等于真实临床部署效果。

**反驳 / 反例**：

1. EHRFlowBench 当前代码快照没有真实参考答案，模型评审分数属于代理指标，可能受到评审模型和报告格式影响。
2. 经验记忆可能跨任务污染、过时或把机构特定规则错误迁移到新机构；论文提出的隔离和生命周期机制仍需真实多中心验证。
3. 公开去标识数据上的沙箱成功，不能直接证明能处理真实医院权限、隐私、编码冲突和医生责任边界。

**边界**：它最适合科研分析流程的自动化和审计，不应被描述为自动诊断或可直接替代专家。

**替代解释**：性能提升可能部分来自更长的重试预算、更强的执行 / 评审模型、工具配置和产物要求，而不是单独来自“自演化记忆”。

**状态**：四智能体、风险规则、评估字段、经验写回门槛 = 本地源码可复核；真实临床迁移 = 还没做；用户文章中的 benchmark 数字 = 待一手核验。

## 五、我现在应该争取什么活

### 第一选择：EHR 治理评估小闭环

目标不是“把 200 例再跑一遍”，而是从已完成的 L1 / L2 产物中抽取匿名元数据，构造一组可评估任务：

- 分类是否正确；
- 脱敏是否漏检或误删；
- 缺失状态是否被正确区分；
- 表格行中的项目、数值、单位和时间是否绑定；
- 病例级答案是否有来源证据；
- 失败时是否进入 Quarantine。

产出应是任务定义、baseline、指标、错误样例索引、护栏清单和一张结果表。未获授权前不读取或外发病历正文。

### 第二选择：PAI 风格缺失状态实验

前提是有获批的病例级 L3 数据、人工金标准、明确预测任务和固定切分。先做“缺失状态编码 vs 传统插补”的小对照，再决定是否实现可学习 prompt；不把 PAI 名称写进成果，除非完成代码、配置、基线和复现记录。

### 第三选择：CMR 模型评估 / 泛化

如果 EHR 的标签和权限短期无法满足前两项，CMR 仍是最稳妥的训练入口：公开数据复现 U-Net / nnU-Net，随后申请现有模型的跨中心评估或少样本微调，交付 Dice / HD95、固定划分、失败案例和实验表。

## 六、给师兄 / 老师的准确说法

> 我最近读到 PAI 和 HealthFlow，感觉它们分别对应“缺失表示如何服务下游任务”和“EHR 分析链路如何被审计”。我不想只把数据治理做成清洗流水线，也不想没有标签就直接训练模型。能否从现有项目里给我一个小闭环：先在匿名、获批的数据上定义一个治理或模型评估任务，固定切分和指标，做 baseline，再负责一组对照和失败分析？如果 EHR 近期还不能进入模型，我也可以先做 CMR 现有模型的跨中心评估。

## 七、对外表达边界

- 可以说：我阅读并分析了 PAI / HealthFlow，并把其中的缺失状态、风险护栏、证据审计思想映射到自己的 EHR 治理路线。
- 暂不能说：我复现了 PAI、参与了 HealthFlow、训练了对应模型、证明了某方法在当前数据上有效。
- 简历中优先写真实治理、评估脚本、指标表和失败分析；阅读论文只能作为学习背景，不能冒充项目成果。
