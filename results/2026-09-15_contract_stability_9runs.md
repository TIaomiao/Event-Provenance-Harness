## 四、四条结论

**结论 1：上一轮的"引用崩溃"是输出被截断造成的，不是模型能力问题。**
把 `max_tokens` 从 8000 提到 16000 后，**9 次运行的引用可解析率全部 100%**（上一轮 CASE-05 rep1 只有 113/547）。
→ **主表必须先报"引用可解析率"**：它低的时候，后面的接地率全部无意义。

**结论 2（本轮最重要的正结果）：`time_refs` 完全成功，9 次运行全部 100%，零跨度。**
对比加 `time_refs` 之前：时间接地**测不出来**（0/141，因为时间与值物理上不在同一行）。
→ **一个 I/O 定义改动，解锁了一个稳定可测的维度。这是"输入输出定义清楚"能带来什么的最硬证据。**

**结论 3：行数完全稳定。** 每个病例三次运行的行数一模一样（143/143/143、111×3、127×3），说明抽取规模可复现。

**结论 4：剩下的唯一不稳定项是"项目名接地"，而且原因是引用粒度。**
CASE-05 rep1 是 `item=0/143` 但同时 `value=143/143` —— **那一次模型只引用了含值的那一行，没有引用项目名所在行**。
其余 8 次都是 100%。
→ **`source_refs` 需要明确"必须包含项目名所在行"**，否则模型有时会只引值行。

## 五、累计的契约改动清单

| 字段 / 规则 | 状态 | 实测依据 |
| --- | --- | --- |
| `scalar_answers.confidence` | ❗ 需增加 | 否则 AUC 画不出来 |
| **`event_tables.time_refs`** | ✅ **已验证：9 次 100%，零跨度** | 时间接地由不可测 → 稳定可测 |
| `source_refs` 定义为"观测所在行的证据集合" | ✅ 基本可用 | 值/单位接地稳定；项目名需再约束 |
| `source_refs` **必须包含项目名行** | ❗ 需明确写入契约 | 1/9 次模型只引了值行 |
| 引用可解析率作为第一道闸 | ❗ 需写入评分协议 | 截断时全部指标失效 |

| `max_tokens ≥ 16000` | ❗ 运行配置 | 8000 会导致截断与指标全面失效 |
